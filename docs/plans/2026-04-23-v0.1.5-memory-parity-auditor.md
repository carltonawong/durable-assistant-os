# DAOS v0.1.5 Memory Parity Auditor Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task if the implementation grows beyond the first slice.

**Goal:** Add a small script-first memory parity auditor that can tell whether a DAOS-style install is actually aligned with the memory model, not merely whether files exist.

**Architecture:** Keep this as a conservative stdlib script under `scripts/`, backed by unit tests. The first slice audits local markdown/file semantics only; runtime adapters and cron integration remain future work unless proven necessary.

**Tech Stack:** Python stdlib, existing `scripts/daos_core` package, unittest/pytest-compatible tests.

---

## v0.1.5 release theme

**DAOS v0.1.5 — memory parity verification.**

This should be a patch release because it hardens verification around the existing architecture. It should not introduce a new memory layer or runtime dependency.

## Acceptance criteria for the first release slice

A user can run:

```bash
python scripts/daos_memory_parity.py /path/to/daos-pack
```

and get:
- `Status: healthy / watch / drift`
- `Findings:` with concrete mismatches
- `Repairs made:` as `none` for the first read-only slice
- `Recommended next move:`

The first slice should detect:
1. Required baseline memory files are present.
2. `wiki/log.md` is chronological append-order: newest dates at the bottom.
3. `wiki/cache/hot-cache-log.md` is reverse-chronological: newest dates at the top.
4. `hot-cache.md` has the five required sections from `HOT-CACHE-SPEC.md`.
5. `AGENTS.md` or pack docs encode local-thread-first/read-order semantics.
6. Raw/source/wiki boundaries are present through `wiki/raw/README.md` and `wiki/sources/README.md`.
7. `agent-continuity.md` has a visible freshness marker if it contains per-agent fallback material.

## Non-goals for v0.1.5 first slice

- no cron scheduler changes
- no live runtime hook integration
- no automatic repair by default
- no broad architecture rewrite
- no new required memory surfaces beyond the current baseline

## Task 1: Add parity result model

**Objective:** Create a tiny reusable result object for parity findings.

**Files:**
- Create: `scripts/daos_core/parity.py`
- Test: `tests/test_daos_memory_parity.py`

**Implementation notes:**
- Use `dataclass`.
- Finding fields: `severity`, `message`.
- Status rule:
  - any `error` => `drift`
  - any `warning` => `watch`
  - none => `healthy`

**Verify:**
```bash
python -m pytest tests/test_daos_memory_parity.py -q
```

---

## Task 2: Check log ordering semantics

**Objective:** Detect the concrete bug surfaced by OPC/Jarvis: `wiki/log.md` and `hot-cache-log.md` use opposite ordering rules.

**Files:**
- Modify: `scripts/daos_core/parity.py`
- Test: `tests/test_daos_memory_parity.py`

**Rules:**
- Extract dates from markdown headings that begin with `## YYYY-MM-DD`.
- `wiki/log.md`: dates should be non-decreasing from top to bottom.
- `wiki/cache/hot-cache-log.md`: dates should be non-increasing from top to bottom.
- If fewer than 2 dated headings exist, do not warn.

**Verify:**
```bash
python -m pytest tests/test_daos_memory_parity.py -q
```

## Task 3: Check hot-cache shape

**Objective:** Verify the installed hot cache looks like a DAOS front-door surface.

**Files:**
- Modify: `scripts/daos_core/parity.py`
- Test: `tests/test_daos_memory_parity.py`

  - `Current Focus`
  - `Current Corrections`

  - `Open Problems`
