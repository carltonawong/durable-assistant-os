# DAOS Setup Philosophy

## Why this page exists

This page is the short doctrine layer behind setup.

If you want to actually run first install, use:
- `docs/quickstart.md`
- `harness/core-setup.md`

## Core stance

DAOS setup should:
- start from lived reality, not system internals
- lock the smallest useful defaults first
- stay short enough to finish in one sitting
- become more tailored through calibration later

DAOS setup should not:
- demand a giant biography capture
- force a full ontology before value appears
- confuse completeness with usefulness
- impress through complexity

## What a first-pass setup must lock

A minimum viable setup should make these explicit:
- assistant charter
- top-level lane map
- memory defaults
- trust defaults
- reminder / planning defaults
- calibration-after-use rule

That is enough to create a usable baseline.
Anything beyond that should be earned by real use.

## Interaction style

DAOS setup works best when it is:
- one question at a time
- low-bloat in wording
- willing to use sensible defaults when stakes are low
- explicit about behavior and approval boundaries early

If setup already feels heavy, the framework is losing.

## Success test

A first-pass setup is successful when the assistant can:
- stay oriented around the right active lanes
- use predictable ask-vs-act behavior
- respect approval boundaries
- reduce repeated steering
- feel net useful before deeper calibration exists

## Calibration is part of setup

A good setup deliberately leaves room for later questions such as:
- what feels too heavy?
- what still gets missed?
- which lane loses the foreground incorrectly?
- which reminders help versus annoy?
- what should be strengthened, softened, added, or removed?

This is why DAOS prefers progressive setup over giant intake.

## Bottom line

Use DAOS setup to create a working baseline, not a total theory of the user.

Start light.
Get useful.
Calibrate later.
