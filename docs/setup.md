# DAOS Setup Philosophy

## Why this page exists

DAOS is not trying to win by collecting the biggest intake form.
It is trying to become useful quickly and then improve over time.

That means setup is not a giant life-modeling exercise.
It is a controlled first-pass install that locks the smallest useful defaults, proves value early, and leaves room for later calibration.

## The setup stance

A good setup flow should begin with the user's lived reality, not system internals.

The wrong opening questions are usually things like:
- what is the universal ontology?
- what are the canonical data structures?
- how many memory layers should exist?
- what is the fully generalized assistant schema?

Those questions can matter later.
But they are usually the wrong way to start helping a real human.

The right early questions are more practical:
- what matters most right now?
- what are the top few active lanes?
- what keeps slipping?
- what kind of help actually feels useful?
- what behavior would make the assistant more trustworthy?

## Progressive setup, not giant intake

DAOS favors progressive setup.

That means:
- ask only what is needed to start
- keep the initial install short
- avoid giant biography capture
- avoid forcing the user to model their whole life before value appears
- deepen later through review, calibration, and actual use

The goal is not to produce a complete theory of the user.
The goal is to produce a working baseline that is already helpful.

## What core setup should lock

A minimum viable DAOS setup should make these explicit:
- assistant charter
- top-level lane map
- memory defaults
- trust defaults
- reminder / planning defaults
- calibration-after-use rule

That is enough to create a durable starting posture without pretending the framework is already finished.

## One question at a time

DAOS works best as a setup wizard rather than a questionnaire dump.

The preferred interaction style is:
- one targeted question at a time
- low-bloat wording
- sensible defaults where ambiguity is low-stakes
- clear locking of important behavior defaults

This style does two things at once:
- it reduces setup fatigue
- it makes the assistant easier to trust from the beginning

If setup already feels heavy, the framework is losing.

## Early usefulness before completeness

DAOS treats early usefulness as more important than exhaustive completeness.

That means a setup is successful when it can do things like:
- orient around the right active lanes
- stop repeating the same avoidable questions
- use stable ask-vs-act rules
- respect approval boundaries
- support task/reminder behavior in a way that already feels net-positive

A setup can still be incomplete and be good.
It fails when it is elaborate but not yet useful.

## Behavior defaults matter early

Behavior should be locked early enough to shape the rest of setup.

At minimum, a first-pass charter should clarify:
- what the assistant is for
- what would make it feel unhelpful fastest
- when it should ask versus act
- what always needs approval
- what kind of presence or feel the user wants

This is why DAOS keeps setup close to:
- `harness/core-setup.md`
- `templates/assistant-charter-template.md`
- `templates/operating-profile-template.md`

The point is to establish behavior before context sprawl makes the system fuzzy.

## Calibration later is part of setup

A DAOS install is not complete because it predicts every edge case.
It is complete when it leaves a clear place for later calibration.

A good setup should end with explicit later-review questions such as:
- what feels too heavy?
- what still gets missed?
- which lane loses the foreground incorrectly?
- which reminders feel useful versus noisy?
- what boundaries should become stronger or softer?

This turns adaptation into a designed part of the system instead of an emergency repair process.

## What DAOS setup is not trying to do

DAOS setup is not trying to:
- fully classify the user's life in one pass
- lock one universal ontology
- solve every future edge case before use begins
- replace real learning through ongoing operation
- impress the user with complexity

A setup flow that asks for too much too early creates friction, not durability.

## Bottom line

The DAOS setup philosophy is simple:
- start from lived reality
- lock only the highest-leverage defaults
- keep the install light enough to finish
- make the assistant useful early
- calibrate later instead of over-designing upfront

A durable assistant should become more tailored as it matures, not harder to adopt at the beginning.
