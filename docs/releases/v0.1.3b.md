# DAOS v0.1.3b

Release date: 2026-04-22

## Intended scope

`v0.1.3b` is a tiny doctrine patch on top of `v0.1.3`.

It does not change the DAOS pack schema or add a new runtime layer.
It sharpens one behavioral rule in the shared-memory model: the hot front door is shared volatile context, not private memory for one agent.

## Changes

### Changed
- `docs/memory.md` and `docs/public-memory-page.md` now describe the front door more explicitly as shared volatile orientation context that may be overwritten as the foreground shifts.
- `starter-pack/wiki/cache/HOT-CACHE-SPEC.md` and `starter-pack/wiki/cache/MEMORY-OPERATING-MODEL.md` now teach that overwrite/re-scope is normal and that recent front-door history should be checked before deeper continuity recovery when the live front door feels mismatched.
- The filled starter-pack example now mirrors the same rule.

### Hardened
- DAOS now says more clearly that no single agent owns the hot-cache/front-door surface.
- DAOS now says more clearly that "someone overwrote the front door" is often normal multi-lane behavior rather than automatic corruption or bad intent.
- DAOS now says more clearly that resume recovery should prefer local thread plus recent front-door history before falling back to deeper per-agent continuity.

## Explicit non-goals

- no DAOS pack-schema change
- no page-metadata change
- no new runtime integration layer
- no change to `LaneSnapshot.status`

## Release intent

Use this patch to make shared-memory behavior less confusing in real multi-agent or multi-lane operation:
- the front door should stay useful without being mistaken for private scratch memory
- overwrite/re-scope should read as normal behavior when the foreground shifts
- deeper continuity should stay a fallback, not the first explanation for every mismatch
